# infra-k3s-gitops

GitOps configuration for a home lab k3s setup, structured to mirror the patterns you'd find in a small production environment: multiple environments, declarative infrastructure, and automated reconciliation via [Flux](https://fluxcd.io/) instead of manual `kubectl apply`.

This is a home lab and a learning environment, not a production system with production guarantees. Expect the structure, tooling, and conventions here to change as new things get tried and better patterns get found — nothing in this repo should be treated as a stable, long-term interface.

## What this repo does

This repo is the single source of truth for what runs on the k3s cluster(s). [Flux v2](https://fluxcd.io/) watches this repository and continuously reconciles cluster state to match what's committed here — push a change, Flux applies it, no manual intervention required.

Each environment under `clusters/` bootstraps its own Flux instance, pointed at its own path in this repo:

```
clusters/
├── stage/    # pre-production — try changes here first
│   └── flux-system/
└── prod/     # production — promoted changes only
    └── flux-system/
```

- `gotk-components.yaml` — the Flux controllers themselves (source, kustomize, helm, notification controllers), generated by `flux bootstrap`. Do not hand-edit.
- `gotk-sync.yaml` — defines the `GitRepository` (where to pull from) and `Kustomization` (which path to reconcile) for that cluster. Also generated; do not hand-edit.
- `kustomization.yaml` — the local Kustomize manifest tying the above two together.

## Where these clusters — and Flux itself — come from

Nothing here is stood up by hand. The sibling repo [`infra-k3s-bootstrap`](../infra-k3s-bootstrap) owns the whole lifecycle of the `stage` and `prod` k3s clusters: Terraform provisions the VMs on Proxmox, Ansible hardens the OS and installs k3s, and a final CI stage runs `scripts/bootstrap_flux.sh <env>`, which calls `flux bootstrap gitlab` against this repo — pointed at `clusters/<env>` on `main`. That's what generates and commits the `gotk-components.yaml` / `gotk-sync.yaml` files above; it's also why they carry the `DO NOT EDIT` header and why re-running the bootstrap is the correct way to change them, rather than editing by hand.

In short: `infra-k3s-bootstrap` builds the clusters and points Flux at this repo; this repo (`infra-k3s-gitops`) is what Flux reconciles once it's watching.

## Why stage and prod

Running two independent environments — rather than one cluster — simulates the promotion workflow of a real production setup: changes land in `stage` first, get verified, then get promoted to `prod`. It's overkill for a single-user home lab in the strict sense, but that's the point — the goal here is to practice the operational discipline (environment separation, GitOps-only changes, no snowflake config) that a small production environment would demand.

## How to make changes

1. Add or edit manifests under the appropriate `clusters/<env>/` path (application workloads, infrastructure components, etc. — the `flux-system` directories themselves are Flux's own bootstrap output and should be left alone).
2. Commit and push to `main`.
3. Flux picks up the change automatically (default reconciliation interval: 10 minutes for `Kustomization`, 1 minute for `GitRepository` polling) or force it immediately with `flux reconcile kustomization flux-system`.
4. Verify in `stage` before making the equivalent change in `prod`.

## Current state

Both clusters are bootstrapped with Flux v2.9.5 but don't yet have any application workloads defined beyond the Flux system itself — this is the scaffolding for what comes next.
